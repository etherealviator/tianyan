# 天衍知识库 — 设计决策记录

## 决策 1：vault 即知识库，不另建独立存储

**背景**：需要让天衍拥有跨会话可读写的知识积累能力。

**决策**：直接使用 Obsidian vault 作为知识库存储层。不建独立数据库或外部存储。

**理由**：
- vault 已在本地，与 Reasonix 在同一文件系统
- .md 格式天然可读，不依赖特定软件
- 用户可在 Obsidian 中直接浏览、修改、链接

## 决策 2：文件系统直写 vs REST API

**讨论**：
- 文件系统直写（read_file/write_file）目前已可用，但只能盲读——无 graph 查询、无 tag 聚合、无 semantic search
- REST API（Obsidian Local REST API 插件）可提供结构化查询能力，但需额外安装插件

**当前状态**：待 REST API 插件安装后验证连通性。验证通过后优先走 API。

## 决策 3：目录结构

```
/
├── inbox/        ← 自动沉淀入口，未经分类的新知
├── domain/       ← 按领域积累的知识维度
└── tianyan/      ← 天衍框架自身的版本演进和架构决策
```

- 不使用数字前缀排序（对 AI 无意义）
- 不嵌套过深（两层足够，递归读取开销小）

## 决策 4：写入触发门槛

待定。在 XML 中嵌入 obsidian_interface 协议时一并定义。

候选触发条件：
- 框架版本号发生变更
- 架构决策被确定（非临时尝试）
- 调试定位到根本原因
- 散道重修发现新维度
- 用户显式要求记录

**不写入的情况**：
- 临时调试过程
- 未采纳的方案
- 日常问答

## 待决问题

- 跨会话读取：新对话启动时能否自动扫描 vault？依赖 Reasonix 平台能力，需实际验证。
- 偏好积累：奖赏制度应放在 XML 的 cognitive_laws 还是 behavior_protocols？
