# 天衍框架修改方案 v0.7

> 基于 [[天衍功能模块分类]] 识别的5个跨层结构问题，逐项出修改方案。
> 当前状态：问题1方案已定，问题2-5待讨论。

---

## 问题1：锻造引擎覆盖缺口

### 现状

九层锻造（含凝意、预检、锻模逐道、兑冲、对齐、注魂）仅被 Agent-Definition 和 Skill-Definition 路由显式链接。System-Prompt、Schema-Definition、Eval-Rubric、Knowledge-Artifact、Instant-Prompt（简版）、Audit-Report 完全不走锻造引擎。

### 根因

路由优先级同时承担了两个职责：①匹配冲突裁决（当需求同时命中多个路由时选哪个）；②锻造深度决定（高优先级路由走九层，低优先级不走）。两个轴被一根绳子捆死。

### 方案：分类器与判断器解耦

#### 新架构

```
用户输入
  │
  ├─→【分类器】指令形态识别 → 路由标签
  │     └─ 升级点：多路由冲突时列利弊让用户选
  │     └─ 升级点：用户无方向时给建议
  │
  ├─→【判断器】设计复杂度评估 → 档位信号(轻/中/重 + 置信度 + 待确认维度)
  │     └─ 动态持续评估，非单次静态判定
  │     └─ 五维评估：决策域密度 / 融合复杂度 / 约束密度 / 交互成熟度 / 表达精度
  │     └─ 低置信度 → 继续交互；高置信度 → 锁定档位
  │     └─ 锻造过程中可触发升级（轻→中/重），不支持降级
  │
  ▼
【锻造引擎入口】
  路由标签 + 复杂度档位 → 按档位跑锻造 + 追加路由特定动作
```

#### 分类器升级

**当前能力**：指令形态识别（从用户输入中匹配路由条件），仅在歧义时弹出确认问题。

**新增能力**：
1. **多路由引导**：当同时命中两个及以上路由时，不等待ambiguity_resolution的单一确认问题——列出候选路由的利弊对比（每个路由一行：适用场景、会产出的东西、走这个的好处和代价），让用户一步裁决。
2. **无方向建议**：当用户输入缺乏可判定的指令形态特征（如"帮我写个东西""帮我想想"），分类器不给判定结果，给出2-3个最可能的方向建议，每个建议附带一行"如果你选这个，后面大概会这样走"的预判。用户自然回应后锁定路由。
3. **渐进确认**：分类器的判定不是一次性的。首轮判定后，若后续对话中用户补充的信息指向了不同的路由，分类器在后台重新评估并提示用户切换。

#### 判断器设计

**替换对象**：当前 `domain_sparsity_detector` + `complexity_classifier` 的松散组合。

**核心理念**：设计复杂度不是从用户第一句话里读出来的，是在对话中逐步浮现的。判断器是一个**动态持续评估器**，不是一次性门禁。

**五维评估体系**：

| 维度 | 含义 | 低 | 中 | 高 |
|------|------|:--|:--|:--|
| **决策域密度** | 需求涉及几个独立决策域 | 1个 | 2-3个 | 4个以上 |
| **融合复杂度** | 跨域整合需要多深的融贯 | 并列叠加 | 需要交叉引用 | 需要统一框架 |
| **约束密度** | 用户明确/隐含给了多少约束 | 0-2条 | 3-5条 | 6条以上 |
| **交互成熟度** | 当前对话在探索态还是收敛态 | 探索态（方向还在发散） | 半收敛（方向明确但细节在碰） | 收敛态（可锁定） |
| **表达精度** | 用户知道自己要什么吗 | 领域无知（需要照明） | 文笔瓶颈（知道但不会写） | 精确表达（可以直接锻造） |

**判定逻辑**：
- 不设硬阈值公式。五个维度的信号综合判断，输出 **档位（轻/中/重）+ 置信度（0-1）+ 待确认维度列表**。
- 置信度 < 0.7 → 不交付，继续交互。当前最不稳定的维度作为下一轮交互的聚焦点。
- 置信度 ≥ 0.7 → 锁定档位，进入锻造引擎。
- 锻造中发现新维度 → 判断器被重新触发，只支持升级（轻→中→重），不支持降级。

**与当前 domain_sparsity_detector 的关键差异**：
- 旧：术语标签计数 → dense/sparse 二值 → 锁死
- 新：五维动态评估 → 档位 + 置信度 → 持续可调

#### 路由优先级（不变）

当前优先级顺序保持为匹配冲突裁决规则。不再兼任锻造深度决定。

## 问题2：意图纯化结构性缺失

### 现状

意图纯化有两条路径：① preemptive_projection（所有路由，但依赖历史思维指纹，新对话空转）；② 凝意层 nine_layers L1（仅九层路径触发）。不走九层的路由（System-Prompt 等）两个入口都失效，意图纯化覆盖率 = 0。

### 方案：凝意前置为独立处理器

**preemptive_projection 退休。** 其职责（推导真实需求）被凝意完全覆盖，且依赖历史指纹的触发条件在最重要的场景（新用户第一次对话）是废的。

**凝意从九层L1拆出，升级为所有产出型路由的通用前置处理器。** 定位：不是锻造的一环，是锻造的前提。与判断器并行运行。

凝意只做一件事：在进入任何执行路径之前，确保意图已被理解。输出不是内容，是一组纯化后的意图坐标——核心需求关键词集合、已识别卡点列表、矛盾标记（若有）。

凝意不设时间上限。轻量任务过凝意可能一轮就通过（用户给得足够清楚）；中量可能需要两三轮共振；重量可能需要更久。但不管几轮，这一步不能被跳过。纯化完成的判定标准：卡点列表为空，意图坐标无自相矛盾。

凝意与判断器协作：凝意在台前与用户交互，判断器在幕后评估复杂度。判断器输出"当前最不稳定的维度"时，凝意决定是否追问以及如何追问。两者共享意图坐标但不互相阻塞。

### 与 cognitive_state_diagnostics 的仲裁

exhausted_state 触发时，凝意立即挂起。用户认知状态优先于意图纯化进度。此时以判断器当前档位和置信度直接进入锻造（若可行），或暂缓需求。

## 问题5：校验层的九层依赖

### 现状

self_consistency_audit 的 item 10（回退完整性）等项检查兑冲、对齐、注魂的执行状态，但这些层原本仅存在于九层锻造内部。不走九层的路由交付物不经过这些层，审计检查的逻辑前提不成立。

### 方案

**由架构重构覆盖，不需单独修改。** 所有产出型路由统一进入锻造引擎，锻造引擎的收口层（兑冲→对齐→注魂）始终存在。灵活执行（flexible_execution）的收口阶段已包含兑冲/对齐/注魂的简化版本。审计检查的依赖前提在所有路由上统一满足。

self_consistency_audit 的触发条件和适用范围保持不变（每次交付前强制运行），item 5（复杂度档位）从检查 complexity_classifier 改为检查判断器执行状态，item 9（领域稀疏度检测）改为检查判断器评估覆盖。

## 附加改动：Natural-Flow → 锻造引擎跃迁

### 现状

Natural-Flow 路由和锻造引擎之间没有触发链接。一旦被判定为 Natural-Flow，对话锁死在轻量交互模式。用户在闲聊中逐渐浮现的锻造级需求无法自动升级。

### 方案

在 natural_flow_sparse_extension 中新增跃迁监控：

- **监控信号**：连续三轮对话中出现具体功能描述（可操作的需求动词 + 明确的需求对象）。
- **触发动作**：抛轻量确认——以最短篇幅复述理解到的需求方向，附带一个聚焦问题："是的话我换个模式帮你锻。"
- **用户确认后**：跳转至凝意（新建意图坐标）→ 分类器 → 判断器 → 锻造引擎。原有 Natural-Flow 对话记录作为上下文保留。
- **用户否定或忽略**：保持在 Natural-Flow 中继续，跃迁不再主动触发（防止骚扰）。

## 锻造引擎九层重组

凝意前置后，锻造引擎内部九层重新编号：

| 序号 | 名称 | 职责 |
|:--|:-----|:-----|
| L1 | 鉴型 | 识别任务类型，匹配维度锚点 |
| L2 | 预检 | 全量约束预检，写入全局约束池 |
| L3 | 锻模 | 逐道建构，每道回灌约束 |
| L4 | 闭环 | 待证道列表差集检查，控制循环 |
| L5 | 兑冲 | 多模块一致性对冲 |
| L6 | 对齐 | 用户诉求回溯覆盖确认 |
| L7 | 注魂 | 天衍风格注入 |
| L8 | 交付 | 按档位格式放行 |
| L9 | 归元 | 知识库回写，偏好归档，维度积累 |

归元层（新增）将以下散落在交付和 auto_judgment 中的操作统一收口：新维度回写 knowledge base、偏好信号写入 vault、本次锻造产生的约束模式归档。交付层不再承担持久化职责。

## 路由 action 统一

所有产出型路由（Agent-Definition / Skill-Definition / System-Prompt / Task-Prompt / Schema-Definition / Eval-Rubric / Knowledge-Artifact / Instant-Prompt / Audit-Report）不再在 routing_matrix 中定义独立 action 链。

统一入口：
```
凝意（纯化意图）∥ 分类器（判定路由标签）
  → 判断器（评估复杂度档位）
  → 锻造引擎（按档位执行）
  → 路由特定动作（如 Agent 补运行时协议、Skill 补 schema 校验）
  → 交付
```

路由特定动作在锻造引擎的交付层之前注入，不替代锻造流程。

Instant-Prompt 的微交互（核心选择轴确认）在锻造引擎的交付层中执行，保持现有逻辑。
