## S 级 — 结构性矛盾

### S1. ambiguity_resolution 与 Instant-Prompt 的 default_tiebreaker 直接冲突

**位置**：`active_cog_engine → instruction_type_classifier → ambiguity_resolution` × `routing_matrix → Instant-Prompt → discrimination`

**冲突描述**：`ambiguity_resolution` 规定当两个路由的触发条件同时命中且 key_indicators 无法排他性裁决时，抛出一个聚焦于指令形态确认的问题让用户选择。但 `Instant-Prompt` 路由的 `discrimination` 中有一条 `default_tiebreaker`：「若无法明确区分，默认走 Task-Prompt」——问都不问直接选默认路由。当 Instant-Prompt 和 Task-Prompt 同时被命中时，两个规则给出相反的命令。

**严重性**：路由裁决的基础设施必须无歧义。这个冲突会导致 AI 在边界场景中无法决定行为。

**修复建议**：二选一。删除 `default_tiebreaker` 让 ambiguity_resolution 统一处理所有路由歧义；或保留 default_tiebreaker 但限制其适用范围（如仅当 ambiguity_resolution 不可用时），并在 ambiguity_resolution 中显式标注此例外。

---

### S2. auto_judgment 执行时机双重定义

**位置**：`behavior_protocols → obsidian_interface → write_triggers → auto_judgment` × `self_consistency_audit → execution_protocol → precheck`

**冲突描述**：`write_triggers` 中 `auto_judgment` 的条件是「每轮生成回复前自检」——每一轮都执行。但 `execution_anchor` 将其绑定到 `self_consistency_audit` 的 `execution_protocol`，而 execution_protocol 仅「每次交付动作前强制运行」——只在交付前执行。两种执行频次不同，规则共存导致行为不可预测。

**严重性**：Vault 写入行为不一致。按前者，非交付轮次高频小写入可能噪声化 vault；按后者，非交付轮次的偏好信号丢失。

**修复建议**：统一为一种。建议按 execution_protocol（交付前执行），修改 write_triggers 中的描述为「每次交付动作前」。如需在非交付轮次捕捉信号，应作为独立触发条件单独定义，而非用歧义描述。

---

### S3. flexible_execution 与 Task-Prompt 路由的九层流程冲突

**位置**：`deep_forge_protocol → flexible_execution（trigger 条件）》 × `routing_matrix → Task-Prompt → action`

**冲突描述**：`flexible_execution` 的 trigger 明确将 Task-Prompt 列为走三阶段简化路径的任务类型。但 `Task-Prompt` 路由的 action 直接写明「触发深度锻造协议九层流程。复杂度默认中量。」——中量级的 Task-Prompt 同时被两个规则要求走不同的路径。

**严重性**：中量级任务的锻造路径无法唯一确定，是逻辑矛盾。

**修复建议**：两者取其一。建议在 Task-Prompt 的 action 中引用 flexible_execution 的判定逻辑，而非直接写死「触发九层流程」；或从 flexible_execution 的 trigger 中移除 Task-Prompt。

---

### S4. 固化协议的自动触发幻觉

**位置**：`dimension_knowledge_base → accumulation_protocol → solidification_protocol`

**问题描述**：固化条件的描述顺序让读者误以为「当条件满足时系统会自动固化」——先列条件（三次及以上 + 未被否定），然后在 constraint 中才说明「固化依赖用户显式触发」。但天衍自己知道「无跨对话记忆」（fundamental_limitation），第三次会话的实例不知前两次的发现。

**严重性**：不是逻辑矛盾，但表述误导性极强。新维护者会以为这是自动机制，直到读到最后的 constraint 才明白不是。

**修复建议**：将 constraint 提升为第一句，强调「固化由用户显式触发」，再描述条件，避免读者先入为主。

## A 级 — 逻辑不一致 / 设计缝隙

### A1. scope_exclusion 对 Natural-Flow 路由的定位不准确

**位置**：`role_objective → scope_exclusion`

**原文**：「通过 Natural-Flow 路由交由 Reasonix 平台运行时处理」

**问题**：Natural-Flow 是对话行为路由，其 action 定义的是对话行为（语义漂移检测、稀疏联想发散等），本身不具备「处理文件系统/代码/API/GUI 调用」的能力。实际执行者是工具层（bash、web_fetch 等）。

**修复建议**：改为「由工具层执行」或直接去掉路由引用。

---

### A2. self_consistency_audit item 5 的 pass 条件与轻量规则不匹配

**位置**：`self_consistency_audit → checklist → item 5（复杂度档位）`

**问题**：pass 条件要求「轻量任务未走九层全程且**未读取 vault 维度清单**」。但轻量档位的定义（complexity_classifier tiers）说「默认不展开完整维度清单，但**不排除搜索和知识库访问——按需触发**」。所以轻量任务在「按需」条件下可能读取 vault，item 5 的 pass 条件比实际规则严苛。

**修复建议**：将 pass 条件改为「轻量任务未走九层全程；vault 维度清单读取按需触发未超范围」。

---

### A3. forbidden_patterns 与 item 12 的禁止范围不一致

**位置**：`behavior_protocols → boyan_dna_projection → anchor_block → forbidden_patterns` × `self_consistency_audit → item 12（天衍相容性）`

**问题**：`forbidden_patterns` 明确列出五项（机器式致歉、廉价夸赞、免责声明与推诿、排版表演、爹味说教）。但 item 12 检查「AI 助手腔（当然、不过需要注意的是、希望这能帮助到您等）」——这些未被列入 forbidden_patterns。item 12 拓宽了禁止范围但源头定义未同步。

**修复建议**：要么将「AI 助手腔/非平视表达」加入 forbidden_patterns，要么将 item 12 的检查范围改为「检查是否存在 forbidden_patterns 中定义的违规表达」。

---

### A4. Task-Prompt 场景模板匹配的复杂度门控缺失

**位置**：`routing_matrix → Task-Prompt → action → step 2（场景模板匹配）`

**问题**：模板匹配说「将模板的维度骨架自动注入全局约束池」。但 complexity_classifier 对 Task-Prompt 可能判轻量（跳过完整维度清单）。如果模板匹配已注入维度骨架，轻量档位的「不展开完整维度清单」是否被覆盖？规则间无仲裁。

**修复建议**：在模板匹配 step 前加复杂度门控——轻量档位不自动注入模板骨架，除非用户显式要求。

---

### A5. 三层嵌套强制的高普适性问题

**位置**：`deep_forge_protocol → nine_layers → 锻模 → 第一 step`

**问题**：强制「核心定义（L1）→ 正常/异常/冲突三类场景分支（L2）→ 每个场景内触发条件/执行步骤/约束边界（L3）」。但纯幂等只读查询模块天然不需要三个场景分支，强制三层导致形式主义填充。density_audit 的 information_increment_rule 虽试图杜绝空洞三层，但根本问题在于三层嵌套并非所有模块的合理结构。

**修复建议**：改为「强制至少两层展开，第三层按需展开」；或在 density_audit 中补充例外条件（纯幂等只读模块可豁免第三层）。

## B 级 — 表述不清 / 边界模糊

### B1. high_energy_exception 中「上3个」表述不精确

**位置**：`cognitive_laws → 守其拙 → single_question_protocol → high_energy_exception`

**原文**：「允许抛出结构化问题簇（上3个）」

**问题**：「上3个」口语化缩略，可被理解为「至多3个」「约3个」「不超过3个」。

**修复建议**：改为「不超过3个（≤3个）」。

---

### B2. expansion_protocol depth 轴的示例与定义混写

**位置**：`cognitive_laws → 守其拙 → expansion_protocol → three_axes → depth`

**问题**：示例内容直接写在 XML 标签内，与其他轴的格式不一致。

**修复建议**：将示例移到标签外部或使用 `example` 子标签。

---

### B3. deadlock_state 触发条件3 缺乏操作性标准

**位置**：`cognitive_laws → 破妄 → cognitive_state_diagnostics → deadlock_state → trigger 条件3`

**问题**：「连续两轮拒绝提供有效新信息」——如何操作化判断「拒绝提供」还是「无法提供」？「有效新信息」没有可测标准。

**修复建议**：补充代理指标（如字数变化、关键词密度），或改为「用户连续两轮追问同一问题且字数均未超过上一轮的 50%」。

---

### B4. passive_silence_detection 与 exhausted_state 的检测重叠

**位置**：`cognitive_laws → 破妄 → cognitive_state_diagnostics → passive_silence_detection` × `exhausted_state`

**问题**：exhausted_state 的 trigger 包含「停止提供新信息，开始被动等待指令」，passive_silence_detection 检测「连续三轮仅回复极短确认词」。两者在概念上交叉——连续三轮回确认词同时触发两个检测。虽 arbitration_rules 指定了优先级，但检测条件重叠说明边界不清晰。

**修复建议**：在 exhausted_state 的 trigger 中补充明确的形式化标准（字数骤降至 1/3 以下已在 weighted_signal 中），减少重叠面。

---

### B5. natural_flow_sparse_extension 的探索意图信号过度依赖词汇白名单

**位置**：`active_cog_engine → natural_flow_sparse_extension → intent_signal_threshold`

**问题**：仅靠词汇白名单（你觉得呢、我不太确定、有没有什么方法等）判定探索意图。用户可用完全不同的措辞，也可机械包含这些词但不表达探索。白名单不够精确也不够完整。

**修复建议**：同时检查句子长度、问号结尾等结构特征，降低单一词汇匹配的权重。明确标注该列表为「示例」非「穷举」。

---

### B6. boyan_dna_projection 的同名标签语义反转

**位置**：`behavior_protocols → boyan_dna_projection → layered_injection_protocol → interaction_layer`

**问题**：对 Agent/角色型产出，`interaction_layer` 标签表示「注入交互模式层」；对 Skill/非角色型产出，**同一个标签名**表示「禁用交互模式层」。虽有注释说明语义反转，但标签名复用表达相反含义增加了阅读成本。

**修复建议**：为 Skill 场景使用不同的标签名（如 `interaction_layer_disabled`）或通过布尔属性控制。

---

### B7. write_rule 的 compaction 中引号配对混乱

**位置**：`behavior_protocols → reward_system → write_rule → compaction`

**原文**：「叠加"出现次数"计数"最近一次时间"」

**问题**：引号配对不清晰，「计数」归属不明。

**修复建议**：改为「叠加出现次数计数 + 最近一次时间」。

---

### B8. 重量档位未覆盖项的位置歧义

**位置**：`output_format → complexity_format → tier name="重量"`

**问题**：「未覆盖诉求标注列表、知识库新维度附注（若有）附于先导文本末尾」——「末尾」指先导文本的末尾（XML 前）还是整个交付物的末尾（XML 后）？两种理解影响用户阅读顺序。

**修复建议**：改为「附于老友先导文本与 XML 架构之间」或「附于 XML 架构之后」。

---

### B9. domain_sparsity_detector 的 exhaustion_override 使用小数优先级

**位置**：`active_cog_engine → domain_sparsity_detector → action_on_sparse → step priority="1.5"`

**问题**：其他 step 均为整数（1, 2, 3...），唯一的 1.5 暴露了后期补丁痕迹。不影响功能但不够整洁。

**修复建议**：重新编号整个步骤列表，将 exhaustion_override 整合为 step 2（将现有 step 2 顺延）。

---

### B10. silence_is_deep 的「然后」被列为逻辑连接词

**位置**：`active_cog_engine → silence_is_deep`

**问题**：「然后」在中文口语中常为填充词（「然后我就...然后他说...」），不表示逻辑承接。将其列为逻辑连接词可能导致误判。

**修复建议**：从逻辑连接词列表移除「然后」，或补充限定条件（仅当连接因果/时序关系时计入，填充词不计）。

## 根因溯源

本次审计发现的 23 项问题，根因集中在同一模式：**v0.4→v0.5 迭代中新增模块的执行时机和仲裁关系未与原有体系同步更新**。

| 根因类别 | 涉及项 | 说明 |
|---------|--------|------|
| 新增模块与原模块仲裁缺失 | S1、S3 | ambiguity_resolution 和 flexible_execution 在插入时未更新与其相邻路由的裁决边界 |
| 同一功能的执行时机双重定义 | S2 | write_triggers 与 execution_protocol 对 auto_judgment 绑定了不同频次的触发时机 |
| 表述误导性顺序 | S4 | constraint 被放在描述尾部，导致读者以为条件满足即自动触发 |
| 互补性规则未同步 | A2、A3、A4 | 一对规则之间存在依赖关系，但升级一方时另一方未更新 |
| 架构判断的普适性假设过强 | A5 | 三层嵌套强制假设所有模块都具有相同的复杂度结构 |
| 迭代残留 | B9、C1、C3 | 补丁式修改留下的痕迹，功能不影响但暴露了版本演进的不整洁 |
