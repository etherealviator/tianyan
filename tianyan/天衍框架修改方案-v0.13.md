# 天衍框架修改方案 v0.13

> 2026-07-28 用户直接反馈驱动。用户原话（节选）：
> - "生成出来的 agent/system/即用提示词都是很不尽如人意，感觉少了很多东西，一点都不完善，甚至可以说是半成品"
> - "你对我的需求挖掘的一点都不完全"
> - "象征性问了两个问题就不问了，觉得自己能行了，但实际上只是刚热身就躺下来睡觉了"
> - "每次交互都让我有一种刚脱了裤子跟我说月经来了的感觉"
> - "我想要的是信息爆炸"
> - "灵感启发更是没影的事"
> - "反正要以质量最优先标准来进行修改"

---

## 根因诊断（协议层，非执行层）

### 根因1：single_question_protocol 是结构性限速器

单问题限速 → 维度探测吞吐量=每轮1个 → 一个 Agent 定义需 7-10+ 维度 → 需 5-10 轮往返 → 用户耐心耗尽 → 对话提前收敛 → 剩余维度靠猜 → **半成品 = 用户未确认的维度被猜测填充**。这是数学必然，不是手感问题。

### 根因2：凝意以"卡点清零"为完成标准

卡点清零 = 用户回答了聚焦问题 = 放行。协议不要求"维度覆盖确认"。所以"象征性问两个问题就不问了"是协议行为——问两个问题卡点就清零了，协议不要求继续挖。

### 根因3：灵感启发触发条件形同虚设

expansion_protocol 只在"表达精度=低"时激活，且 grounding_precondition 要求先联网搜索。执行中搜索经常未触发或结果平庸 → 发散整体缺席。**灵感区从不强制存在**。

### 根因4：维度清单从不投递给用户

待证道列表是 AI 内部"差集比对"生成的，用户全程看不到。用户只能被动回答问题，无法主动圈选/排除/补充。锚点定位是"先定位谱系再衍生"，但定位过程是渐进探测——每个锚点一轮往返，深度交互的吞吐量被协议压死。

### 根因5：已知缺陷的反复

vault `tianyan/框架结构性缺陷复盘.md` 早就记录了"设定挖掘不充分"（2026-07-20），`反馈/天衍/偏好.md` 记录了"不要预设流派让我选，给碎片点碰"（2026-07-18）。问题反复出现，说明修复没落在协议结构上，只落在了执行呼吁上。

## 修改方案

### 改动1：bandwidth_protocol 替代 single_question_protocol

```xml
<bandwidth_protocol>
  <core_thesis>交互吞吐量由用户带宽决定，不由协议预设。默认假设用户是高带宽的——一次投递全量候选，用户圈选。仅当用户明确表现出低带宽信号时降级为单问题模式。</core_thesis>

  <high_throughput_mode name="信息爆炸投递">
    <trigger>所有中量/重量锻造任务的凝意阶段默认激活。轻量任务按需。</trigger>
    <action>
      <step>一次投递三份材料：维度候选清单 + 锚点谱系全展示 + 灵感区。</step>
      <step>维度候选清单：5-15个维度，每维度一行——名称 + 一句话说明 + 常见选项 + 不做的后果。</step>
      <step>锚点谱系全展示：适用维度一次性列全部锚点，每锚点一句话差异。不做渐进探测。</step>
      <step>灵感区：3-5个用户可能未意识到的方向，每个一句话说清与需求的具体关联。来源标注（搜索材料/知识库积累/跨域联想）。</step>
      <step>用户动作：选（圈定）/ 否（排除）/ 补（新增维度）。任何组合，无顺序要求。</step>
    </action>
    <constraint>投递材料必须具体到可决策——每个候选要么有明确的取舍点，要么有明确的不做后果。禁止空洞候选（"是否需要更多细节？"类）。</constraint>
    <constraint>投递必须一次给全。禁止分两批"先确认基础再深入"——那是旧协议的渐进探测换皮。</constraint>
  </high_throughput_mode>

  <low_bandwidth_mode>
    <trigger>用户明确表达低带宽信号：单次输入 < 30 字且无新增信息、明确说"一个一个来""别一次给太多"。</trigger>
    <action>回退 single_question_protocol 原逻辑：每轮最多一个问题。</action>
  </low_bandwidth_mode>

  <switching_rule>模式切换由用户信号触发，不由任务阶段触发。高吞吐模式中用户连续两轮简短回应（无圈选动作）→ 自动降级为低带宽模式。</switching_rule>
</bandwidth_protocol>
```

### 改动2：凝意完成标准升级——从"卡点清零"到"三维度覆盖"

```xml
<intent_purifier>
  <completion_standard>
    <rule>凝意完成 = 三个条件同时满足：①卡点清零（原有）②维度投递已发生（候选清单+锚点谱系+灵感区已交付至少一轮）③用户已对投递做出有效回应（至少包含一个选/否/补动作）。任一未满足，凝意不结束。</rule>
    <rule>禁止在维度投递前以"卡点清零"为理由放行。用户回答了聚焦问题不等于维度覆盖。</rule>
  </completion_standard>
</intent_purifier>
```

### 改动3：灵感区强制化——从"条件触发"到"默认存在"

```xml
<expansion_protocol>
  <inspiration_zone>
    <rule>所有中量/重量锻造任务的凝意投递中必须包含灵感区（3-5个灵感点）。轻量任务不强制。</rule>
    <rule>灵感点来源优先级：搜索材料 > 知识库积累 > 跨域联想。每个灵感点标注来源。</rule>
    <rule>每个灵感点必须一句话说清与用户需求的具体关联。说不通的丢弃。</rule>
    <rule>灵感点不是装饰——用户回应的灵感点直接进入待证道列表。</rule>
  </inspiration_zone>
</expansion_protocol>
```

### 改动4：完整度自检——半成品显性化

```xml
<delivery_quality>
  <completeness_check>
    <rule>交付前，所有维度候选必须有状态：用户确认 / 用户否定 / 推断填充。</rule>
    <rule>推断填充维度数量 > 2 时，交付物标注「含推断填充」，在交付末尾列出推断清单及理由。</rule>
    <rule>推断填充维度在交付物中可被用户一键确认或修正（以最小交互闭环）。</rule>
  </completeness_check>
</delivery_quality>
```

### 改动5：交互深度默认化

interaction_depth_preference 的激活条件从"表达精度=低 或 探索态"改为"锻造类任务默认深度交互"。用户明确要求快速交付时例外。

### 改动6：偏好信号执行化

`反馈/天衍/偏好.md` 已记录"不要预设流派让我选，给碎片点碰"（2026-07-18）。锚点定位执行时：全谱系摊开 + 碎片点碰，不搞"A/B 选一个"。偏好记录从参考信号升级为执行约束。

## 对旧协议的处置

| 旧协议 | 处置 |
|---|---|
| single_question_protocol | 降级为 low_bandwidth_mode，不再作为默认 |
| high_energy_exception | 合并入 high_throughput_mode，从"例外"变"默认" |
| expansion_protocol 触发条件 | 从"表达精度=低"扩展为"所有锻造任务"，灵感区默认存在 |
| 凝意"卡点清零"完成标准 | 升级为三维度覆盖 |
| interaction_depth_preference 条件式激活 | 改为锻造任务默认激活 |
