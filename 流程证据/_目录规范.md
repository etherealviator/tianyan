# 流程证据目录规范

> 锻造履历归档。每条交付物对应一条履历记录，供独立审计实例交叉核验。

## 目录结构

```
流程证据/
├── _目录规范.md              ← 本文件
├── 2026-07-21_Agent-Definition_墨猫-v2.md
├── 2026-07-21_Skill-Definition_搜索工具.md
└── ...
```

## 文件名格式

```
{YYYY-MM-DD}_{路由}_{名称简写}.md
```

- 日期为交付完成日期
- 路由取值与 routing_matrix 一致：Agent-Definition / Skill-Definition / System-Prompt / Task-Prompt / Instant-Prompt / Schema-Definition / Eval-Rubric / Audit-Report / Knowledge-Artifact
- 名称简写：对应交付物名称，不超过 20 字

## 日志来源

锻造履历来自 `forge_log`（天衍锻造引擎中的跨层日志积累模块）。每层执行时自动写入日志记录，L8 交付时从 forge_log 积累中输出完整履历写入此目录。监天审计结果作为 L7.5_监天 层记录自动包含在履历中。

## 履历内容结构

```yaml
---
forge_date: 2026-07-21
route: Agent-Definition
mode: forge | express | unknown
deliverable: 成果/某成果/v1.md  # 关联的交付物路径
integrity: A | B | C            # 流程完整度自评
---
```

## 字段说明

| 字段 | 说明 |
|------|------|
| mode | forge=完整九层；express=省流模式（轻量或用户授权）；unknown=无法追溯 |
| integrity | A=九层+监天完整走完；B=核心层已走但部分跳过；C=省流模式 |
| 状态 | executed / skipped / express |
| 关键证据 | 具体可追溯的证据，不是泛化描述。如"用户原话：xxxx"而非"用户表达了需求" |
| L7.5 监天 | 监天审计的成果类型标签、审计维度组、判定的审计等级、发现的问题清单 |

## 层序说明
- **凝意（前置）** 不属于九层锻模，是锻造引擎之前的意图纯化阶段。单独列出便于追溯完整流程。
- **L1-L9** 严格对应 deep_forge_protocol 中的 nine_layers 定义。
- **L7.5 监天** 在 L7 注魂之后、L7.6 之前执行，履历中按实际执行顺序排列。
- **L7.6 子agent审计** 在 L7.5 监天之后、L8 之前执行。重量档强制执行，中量由判断器决定。被跳过时需注明原因。

## 与成果目录的关系

- 成果/ 目录存放交付物本体——用户使用交付物时看这里
- 流程证据/ 目录存放锻造过程记录——用户核验或独立审计实例交叉验证时看这里
- 两条目录独立，通过文件名中的日期+名称简写关联
- 锻造履历不在交付物中出现，不给用户增加阅读负担

## 外部交叉核验协议

外部独立实例（监天或其他 AI、人工审查、工具分析）读取锻造履历时：

1. 扫描 流程证据/ 目录获取所有履历列表
2. 从履历中读取 route / mode / integrity 过滤感兴趣的目标
3. 对每条履历中的「逐层记录」与「关键证据细节」做合理性判断
4. 交叉核对：履历声称「executed」的层是否在交付物中有对应体现
5. 交叉核对：履历声称「skipped」的层是否有足够的原因说明
6. 交叉核对：监天审计结论（L7.5_监天）与交付物实际质量是否匹配
7. 产出审计报告写入 反馈/审计日志/ 或用户指定位置

独立实例与天衍不共享推理路径。独立实例的推理独立于天衍的推理——这是交叉核验具有博弈价值的前提。监天审计作为天衍内置模块，其结论诚实性由 forge_integrity 身份承诺保障；外部实例核验独立于天衍的内部承诺，两者互为冗余。
